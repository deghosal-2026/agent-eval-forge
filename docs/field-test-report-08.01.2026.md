# Field Test Report — 08.01.2026

**Date:** 2026-08-01
**Status:** Roster expanded to 20 agents; results snapshot preserved; configs generated

## 1. Executive Summary

The field test roster was scaled from 8 to 20 agents by sourcing simple, tool-calling agent repositories from GitHub. Candidates were filtered against the criteria established in `docs/field-test-plan.md` — LangGraph or PydanticAI agent classes (not platforms/frameworks), tool-calling capability, no database dependencies, clear entry points, small-to-mid star counts.

**Key results:** 11 LangGraph + 9 PydanticAI agents pinned to specific commit SHAs. Configs generated for all 12 new agents via `field/gen-field-json.py` heuristics. Previous sweep results preserved under `field/results.08.01.2026/`.

**Why this report matters later:** this is the moment the benchmark stopped being a
curated 8-agent demo and became a real-world compatibility problem. The decisions
made here — broad GitHub sourcing, heuristic config generation, and preserving the
8-agent baseline before expansion — are what made the 08.02 field-test analysis possible.

**Sourcing:** 150+ GitHub repositories searched across multiple query strategies:
- `agent in:name langgraph` (pages 1-3)
- `agent in:name pydantic-ai` (pages 1-2)
- `langgraph agent tools description` + `example/simple/demo` variants
- Follow-on targeted checks for small, low-star repos

Candidate repos were checked via GitHub API for size, fork count, and entry-point structure. Large repos (>3 MB), platforms, frameworks, and database-bound agents were rejected.

**Operational takeaway:** the sourcing step was not just list-building. It defined
the benchmark philosophy: prefer small-to-mid open-source repos that represent how
real developers publish agents, even when that means future curation pain.

## 4. Config Generation

Configs for the 12 new agents were generated by `field/gen-field-json.py` using ranked heuristics:

1. `langgraph.json` → langgraph adapter
2. `create_react_agent` / `StateGraph` → langgraph adapter
3. `pydantic_ai Agent` → pydantic-ai adapter
4. FastAPI app → http adapter
5. `[project.scripts]` → subprocess adapter
6. fallback → list-file adapter

**Resolution summary:**

| Agent | Detected adapter | Config |
|---|---|---|
| lg-mcp-agents | langgraph | auto |
| lg-tools-agent | langgraph | auto |
| lg-mcp-template | langgraph | auto |
| lg-plan-react | langgraph | auto |
| lg-my-agent | langgraph | auto |
| lg-agent-system | langgraph | auto |
| lg-skills | langgraph | auto |
| lg-course | langgraph (unresolved) | needs curation |
| pa-research | subprocess (via script) | needs curation |
| pa-github | http (FastAPI endpoint) | needs curation |
| pa-multi-agent | pydantic-ai | auto |
| pa-weather | pydantic-ai (unresolved) | needs curation |

**Curation notes for the 4 unresolved entries:**

- **lg-course:** Repo is a course with 12+ examples under `src/examples/ex*`. Real tool-calling graph in `examples.ex011.graph.build_graph` (needs a `checkpointer` argument). Not a single runnable agent — requires picking one example module.
- **pa-research:** Has both a PydanticAI agent (`agents.research_agent`) and a `research-email` console script. Detected via `[project.scripts]` → `cli.main:app`, but `cli/main.py` does not exist (only `cli/chat.py`). Should be curated to the `research_agent` module.
- **pa-github:** Contains both a PydanticAI agent (`github_agent.py`) and a FastAPI endpoint (`github_agent_endpoint.py`). Heuristic picked the FastAPI app — but the core agent is the PydanticAI `github_agent`, which is the better field-test target.
- **pa-weather:** `weather_agent.py` defines a module-level `weather_agent = Agent(...)` instance with two tools (`get_lat_lng`, `get_weather`). Heuristic missed the instance (not `def`/`class`); config should point at `module: weather_agent, function: weather_agent`.

### 4.1 What We Underestimated On 08.01

This report correctly identified 4 unresolved configs, but in hindsight it still
underestimated the amount of work required to operationalize the roster:

1. Some repos needed **new packaging metadata** (`pyproject.toml`) just to create a clean env.
2. Several repos used **framework APIs from older pydantic-ai generations**, which
   required compatibility wrappers rather than simple config edits.
3. `src/` layout and async factory patterns meant some repos were only runnable under
   their native CLI/runtime, not from repo-root import assumptions.
4. Python-version and C-extension issues did not show up at sourcing time, but became
   central blockers during the 08.02 sweep.

This makes 08.01 valuable as a historical checkpoint: it shows what can be seen from
static repo inspection versus what only appears during real execution.

### 5.1 Why Preserving The 8-Agent Sweep Was Important

Saving the pre-expansion results under `field/results.08.01.2026/` created a clean
baseline for later comparison. Without this snapshot, it would be difficult to tell
whether pass-rate changes on 08.02 came from:

- broader roster difficulty,
- wrapper regressions,
- judge differences,
- or genuine harness improvements.

This is a useful reporting lesson for future sweeps: once a benchmark scales,
historical snapshots become as important as the latest run.

### 5.2 Narrative Value For Future Writing

This report contains the beginning of a strong benchmark story:

- Day 1 showed that a small curated benchmark can validate harness architecture.
- Day 2 would show that scaling to the open-source wild introduces a different class
  of problems: compatibility, packaging, runtime drift, and framework-version skew.

That before/after shape is strong article material because it moves from “the system
works on examples” to “the system survives reality.”
